# OpenUtau QQ voice replies

The QQ adapter asks Ollama for a JSON response with `reply_text`, `generate_audio`, `voice_text`, and `voice_mode`. Ollama selects `speech` by default and selects `sing` when the user explicitly asks the bot to sing. If audio rendering fails, the bot still sends the text reply.

Ollama returns `voice_text` plus emotion, delivery, ending-intonation, and an emphasized word. The adapter converts Arabic numerals to Japanese readings, then converts kanji and katakana to hiragana with pykakasi. `pyopenjtalk-plus` analyzes Japanese accent phrases and mora readings; ONNX Runtime enables its optional reading prediction for ambiguous standalone `何` (nani/nan). The adapter maps high/low accent patterns to note pitches and a visible PITD curve, with a simple phrase contour as a safe fallback if alignment fails. Speech note lengths vary by mora type, accent, emphasized words, phrase endings, emotion, and delivery; each phrase is normalized to preserve its overall speaking rate while making the rhythm contrast more audible. The speech profile follows Owari's restrained robot persona: controlled pitch accents, minimal dynamics and breath, and no vibrato. Prosody offsets from neutral are currently scaled by 2.5 for a more noticeable effect, with expression ranges clamped where applicable. OpenUtau `vel`, `atk`, `dec`, `bre`, `brec`, and `tenc` expressions are written to generated speech USTX. Speech does not invoke AI Auto Pitch. The common loanword `missile` is also normalized to `ミサイル`; any remaining Latin token is spelled using Japanese letter names so it cannot abort the reply. Punctuation and decorative symbols without phonemes are skipped, while other unsupported letters stop audio generation safely and trigger the text fallback. The QQ text reply remains in the language selected by the conversation.

In `sing` mode, Ollama also returns `song_min_duration_seconds` when the user specifies a length. Song files are read from `songs/*.ustx`; available titles come from those filenames. The adapter scores musical phrases using note density, pitch range and height, melodic movement, dynamics, and repeated interval patterns, then builds candidate excerpts throughout the song rather than anchoring every request to one global peak. It randomly chooses among several high-scoring, separated candidates and avoids the last five successfully rendered excerpts for that song when alternatives exist. Long rests are skipped while complete phrases and short pauses are retained. A requested duration is the target; when the user gives no duration, `song_default_duration_seconds` (10 seconds by default) is used. If a candidate region is shorter, the adapter uses its available complete phrases instead of padding with silence. After successful rendering, the QQ text reply is `正在播放：<source song title>`; if the score is missing or rendering fails, the bot keeps Ollama's normal text reply.

Song excerpts do not use AI Auto Pitch. They retain the pitch, singer, phonemizer, track, and expression data present in the source USTX. The selected USTX is rendered directly by the headless C# renderer; song playback no longer imports a legacy UST through the OpenUtau UI.

Questions about the repertoire or whether the bot can sing a song are treated as questions, not playback commands. For repertoire questions, the QQ adapter sends a text-only numbered list of every title present in `songs/`, in random order; it does not generate speech for this reply. The user can choose by number or title. A valid full number selects that item; if the number is out of range, the first digit is used as a fallback (for example, `32321` selects item 3). Explicit requests such as “sing this for me” still start playback.

## Configuration

Edit `openutau_configs.json` to select the voicebank, template, OpenUtau executable, C# renderer executable, and pace. Set `enabled` to `false` for text-only replies without changing the model prompt.

The generated `.ustx` excerpt and `.wav` files are placed in `openutau_adapter/output/`, which is ignored by Git. Newer USTX templates are converted on generated output to the bundled renderer's supported format; source templates and songs are left untouched. Set `song_default_duration_seconds` in `openutau_configs.json` to adjust the target length when the user does not request a specific duration.

## Proper-noun readings

pykakasi reads proper nouns with ordinary dictionary readings, e.g. 熱音終 becomes ねつおとおわり. `pronunciations.json` maps such words to their correct hiragana (`{"熱音終": "ねつねおわり"}`); the table is applied to `voice_text` and emphasized words before any kana conversion, longest entry first, and is re-read on every reply, so new entries take effect without restarting the bot. Add both Japanese and simplified Chinese spellings when the model may write either.

## Runtime requirements

Install the project and adapter dependencies with `python -m pip install -r requirements.txt -r openutau_adapter/requirements.txt`. Build the headless WAV renderer with `dotnet build openutau_adapter/renderer_host/OpenUtauRenderer.csproj`. Both speech and song rendering use OpenUtau's C# core without opening its UI. NapCat must be able to access the rendered WAV from the same machine to send it as a QQ voice message.
